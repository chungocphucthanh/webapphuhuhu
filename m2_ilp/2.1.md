## 4. Sets, parameters, and `Instance` fields

| Notation | Code field | Meaning |
| --- | --- | --- |
| `I` | Indices of `staff_ids` | People |
| `J` | Indices of `session_names` | Sessions |
| `D` | Keys of `sessions_by_day` | Exam dates |
| `C` | Values of `campus` | Campuses CS1 and CS2 |
| `r_j` | `demand[j]` | Number of people required for session `j` |
| `O` | `overlaps` | Session pairs that cannot share a person |
| `B` | `baseline` | Original assignment pairs `(i, j)` |
| `A` | `A` | Permitted assignment pairs `(i, j)` |
| `pref_i` | `preferences[i]` | Synthetic CS1, CS2, or BAL preference (see [2.6](2.6.md)) |

Indices start at zero. `staff_ids[i]` gives the staff ID represented by `i`. `session_names[j]` gives the session represented by `j`, such as `20260518_5_CS1`. Entries at the same session index in `demand`, `campus`, `day`, and `intervals` describe that same session.

Additional fields provide:

- `intervals[j]`: start and end times as `datetime` objects.
- `day[j]`: the session's start date as a `date` object.
- `sessions_by_day[d]`: session indices on date `d`.
- `seed` and `availability`: the seed and policy used to construct the instance.
- `flip_rate`: the seeded opening probability; `None` under the other policies.
- `soft_weights` and `soft_weight_map`: the seed-derived weights (see [2.6](2.6.md)).

Use `r_j` for demand and `w_i` for workload in the report, keeping them distinct from deviation variables introduced by the objective owner.

## 5. Seeded availability

The default is `availability="seeded"`. It uses baseline history as a starting point without fixing the historical assignments as the only permitted schedule.

### Generation rule

1. Collect observed `(person, shift code)` pairs from the baseline.
2. Keep every observed pair available.
3. Sort staff by staff ID and sort shift codes.
4. For each unobserved pair, draw one value with `Random(seed)`.
5. Open that pair if the value is less than `0.30`; otherwise leave it unavailable in the simulated instance.
6. Apply the result to all campus sessions belonging to that shift code.

There are `73 × 65 = 4,745` possible person–shift pairs. The baseline contains 769 observed pairs. Of the remaining 3,976 pairs, seeded draws open 1,182 additional pairs. Mapping these available shift pairs onto campus sessions gives 2,593 pairs in `A`.

The 30% value is a probability per draw, not a requirement to open exactly 30% of the pairs.

Preserving observed availability prevents this simulation from invalidating baseline assignments on availability grounds. Capacity and overlap still need independent validation. Availability permits consideration of an assignment; it does not force the solver to retain the historical assignment.

Absence from the baseline is not proof of real personal unavailability. It identifies a pair on which this simulation draws a random value. The generated result is a reproducible model input, not an observation of leave, appointments, or other commitments.

### Other policies in the code

| Policy | Rule | Use |
| --- | --- | --- |
| `seeded` | Preserve observed shift availability and open additional pairs with seeded draws | Current v1 default |
| `day` | A person recorded on a date is available for every session on that date | Compare with the earlier proposed policy |
| `shift` | Use the complement of explicitly supplied Busy pairs | Reuse a prepared scenario with known Busy data |

The raw M1 loader leaves Busy unknown (`None`), so `shift` mode requires a scenario with explicit Busy. It raises an error when Busy is unknown. `seeded` mode rejects explicit Busy data so that it cannot silently overwrite supplied restrictions.

### Availability and overlap

Availability determines whether one assignment is permitted. Overlap determines whether two permitted assignments can be selected together for the same person.

Sessions overlap when:

```text
start_j < end_k and start_k < end_j
```

Sessions that only meet at an end/start boundary do not overlap under this rule. Sharing availability across campuses does not allow simultaneous work at both campuses: the hard-constraint owner enforces no double-booking. Travel penalties belong to the soft-constraint component and do not alter this overlap relation.

## 6. Explanation of each function

### `Instance`, `__post_init__`, and `soft_weight_map`

`Instance` is a dataclass that keeps related inputs together. `__post_init__` groups session indices by exam date in `sessions_by_day`, allowing fatigue/travel code to reuse the grouping. The `soft_weight_map` property pairs the ordered weights with their v1 names; it does not implement penalties (see [2.6](2.6.md)).

### `_team_seed(seed=None)`

Read `data/seed.txt` when no seed is supplied. Validate that the seed is an integer and equals the official value for `TEAM_ID`. Rejecting another seed prevents mixing one team's simulated inputs with another team's weights. The underscore marks an internal helper.

### `_checked_pairs(pairs, n, m, label)`

Validate that each item has two integer indices within bounds and return a set. `label` identifies baseline, Busy, or overlap in error messages. Invalid pairs cause an error rather than being silently dropped, which could remove a restriction or corrupt an assignment.

### `available_pairs(data, mode, seed=None, flip_rate=0.30)`

Construct `A` using `seeded`, `day`, or explicit-Busy `shift` rules. Validate the probability and reject a policy that would replace explicit restrictions. Its result is a set of candidate assignments, not a selected schedule.

### `build_instance(seed=None, availability="seeded", data=None, flip_rate=0.30)`

Build the complete M2 input object. Call the M1 loader unless prepared scenario data is supplied. Convert ISO time strings to `datetime` when needed. Validate aligned sizes, positive integer demand, supported campuses, valid intervals, and pair indices. Construct session names, dates, availability, preferences, and weights, then return `Instance`.

This function works in memory: it does not export preferences, construct the ILP problem, or run a solver.

### `toy_instance()`

Return the brief's p. 2 example: three people, Morning and Afternoon sessions requiring two people each, and CB1 unavailable in Morning. There are five available pairs.

Times, campus, and the supplied feasible baseline are illustrative metadata added to fill the fields; they are not real dataset rows. This example differs from the four-session fairness example on p. 5.

### `small_slice(inst, n_days=1)`

Keep sessions from the earliest `n_days` exam dates. Retain people who are available for a selected session or appear in its baseline, including candidates not selected in the historical schedule.

Renumber people and sessions, updating `A`, baseline, overlap, and parameter lists together. Copy existing preferences and weights without resampling. `n_days` counts exam dates, not consecutive calendar days.

The real first-day slice has 25 candidate people, one session, and demand two. The session is `20260518_5_CS1`, on 18 May 2026 from 18:15 to 20:45; its baseline staff are CB001 and CB002. It needs two people, not 25. The seven-exam-date slice has 68 people, eight sessions, demand 37, and 204 available pairs.

Compare a slice's optimized schedule against that slice's baseline rather than against the full-data maximum of 19.

### `print_summary(inst)`

Print counts, availability, baseline pairs outside `A`, workload distribution, preferences, and weights. These statistics support review. Zero baseline pairs outside `A` verifies membership only, not full feasibility under capacity and overlap.

### `main()`

Read command-line options, load data, build and summarize the instance, compare availability policies, export preferences, and summarize the first-day slice. This entry point runs preprocessing, not the M2 production solver.

## 7. Running the preprocessing

From the repository root, with the pinned requirements installed:

```powershell
python -m m2_ilp.instance
```

This reads `data/seed.txt`, prints statistics, and writes `data/simulated_preferences.csv`. It does not write the optimized schedule or final metrics.

For a planned sensitivity comparison:

```powershell
python -m m2_ilp.instance --flip-rate 0.2
```

Record the policy/probability before comparing schedules. Baseline and optimized schedules must use the same instance. Do not change the seed or simulation rule after viewing solver results merely to select a better-looking outcome.

`test_inputs.py` is kept locally for Vinh's development checks and excluded from Git tracking. It is not part of the delivered runtime or an output generator. It checks the data/variable handoff, not the completed M2 model.
