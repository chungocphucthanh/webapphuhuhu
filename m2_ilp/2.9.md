# 2.9 Performance evaluation

[metrics.py](metrics.py) computes metrics for an assignment schedule. [performance.py](performance.py) uses the same measures to compare the baseline and M2 schedules, count model size, and measure solve time.

## Schedule metrics

With $w_i$ denoting the number of sessions assigned to staff member $i$, the metrics are:

| Metric | Calculation |
|---|---|
| `max_load` | $\max_i w_i$ |
| `min_load` | $\min_i w_i$ |
| `spread` | $\max_i w_i-\min_i w_i$ |
| `l1` | $\sum_i |w_i-\bar w|$, where $\bar w=\sum_j r_j/|I|$ |
| `staff_used` | Number of staff members with $w_i>0$ |
| `location`, `fatigue`, `travel` | Soft penalties computed by `evaluate_soft()` |

`loads()` includes staff with no assignments. For example, loads $(2,2,0)$ must give `min_load = 0`, not 2. Each staff–session pair is counted only once; `compute_metrics()` materializes the pairs before computing loads and soft penalties, so it also accepts a generator.

These metrics measure schedule quality; they do not replace checks for staffing, availability, and time overlaps. The demand-derived mean equals the actual mean load when the schedule meets total demand exactly, as explained in [2.3](2.3.md).

For a fair comparison, the baseline and M2 use the same instance, fatigue threshold $K$, and weights. `baseline_comparison()` also computes:

$$L1+\lambda_{LOC}\,LOC+\lambda_{FAT}\,FAT+\lambda_{TRV}\,TRV.$$

This function uses the instance's default weights and $K$ from `fit_fatigue_k(inst)`. If the solution was obtained using different weights or a different $K$, the comparison value may differ from the objective recorded in the solution.

## Model size

Let $n=|I|$, $m=|J|$, $a=|A|$, and $q$ be the number of overlapping session pairs. Assignment variables are created only for available pairs, as described in [2.2](2.2.md).

| Component | Number of variables or constraints |
|---|---:|
| Assignment variables $x_{ij}$ | $a$, rather than $nm$ for a dense model |
| Maximum-load variable $t$ | 1 |
| `MAX` constraints | $n$ |
| Staffing constraints | $m$ |
| Pairwise overlap constraints | At most $nq$ |
| Stage-2 deviation variables $\delta_i$ | $n$ |
| `DEVP`, `DEVN` constraints | $2n$ |
| `TCAP` constraint | 1 |
| `DEVC` constraints, if enabled and the mean is non-integer | $n$ |

Excluding auxiliary variables and soft constraints, stage 1 has $a+1$ variables and stage 2 has $a+1+n$. Each $w_i$ is a sum expression over $x_{ij}$, not a separate variable. Grouping overlapping sessions into cliques changes the row count compared with a pairwise formulation; `size_table()` reports counts by family for the actual model and reference counts for the pairwise formulation.

Polynomial model size does not imply polynomial solve time. The $a$ binary variables alone allow up to $2^a$ assignments before constraints are considered. CBC uses LP relaxations, branching, and cuts; runtime also depends on constraint strength, availability data, and weights. Runtime cannot be inferred from the variable count alone.

## LP bounds and integer solutions

When minimizing the same objective under the same constraints:

$$Z_{LP}\le Z_{ILP}.$$

In stage 1, $\sum_j r_j/n$ is a lower bound on the maximum load. For integer loads:

$$t^*\ge \left\lceil\frac{\sum_j r_j}{n}\right\rceil.$$

Equality does not always hold: some staff may be unable to take the required sessions. Similarly, the chord constraint in [2.3](2.3.md) can improve the stage-2 LP bound, but does not guarantee that it closes the gap to the integer optimum.

Treat the LP value as an optimal bound only when the solver reports optimality. After a time limit, a feasible solution to a minimization problem is an upper bound, not automatically a lower bound. The measurement functions retain solver status alongside the value; `None` means no value is available to report, not zero.

## Hand-calculated example

With 3 staff members and 4 sessions requiring one person each, the load profiles $(2,1,1)$ and $(2,2,0)$ both have `max_load = 2`. However, their `spread` values are 1 and 2, and their L1 values are $4/3$ and $8/3$, respectively. Maximum load alone is therefore insufficient to distinguish how balanced the two schedules are.

## Measurement functions in the code

- `size_table(inst, config)`: count variables and constraints in both stages without solving.
- `lp_bound(inst, config, t_cap=None)`: solve the stage-1 LP, or the stage-2 LP when `t_cap` is supplied.
- `runtime_table(seed=None)`: measure horizons of 1 day, 1–3 weeks, and the full dataset; report each stage's runtime, status, gap, and branch-node count.
- `chord_ablation(inst, config, t_star, time_limit=30)`: compare runs with and without the chord constraint, using the same load cap and time limit.
- `baseline_comparison(inst, solution)`: place the two schedules' metrics side by side.
- `worked_example()`: enumerate the small example, then compare it with the two-stage solution and LP.

The command `python -m m2_ilp.performance` runs the measurements and writes results to `m2_ilp/performance.json`. The functions do not run automatically on import. When using measurement results, record the configuration, seed, solver version, and machine so that runs can be compared under the same conditions.
