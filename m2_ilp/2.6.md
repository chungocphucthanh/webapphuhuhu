## 4. Synthetic location preferences

For each person, let `n1` and `n2` count baseline assignments at CS1 and CS2. The v1 sampling probabilities are:

```text
P(BAL) = 1/3
P(CS1) = (2/3) × n1 / (n1 + n2)
P(CS2) = (2/3) × n2 / (n1 + n2)
```

Without baseline history, use equal probabilities. `BAL` represents a balance/no-single-campus preference; its exact penalty treatment must be specified by the soft-constraint owner.

Campus history provides a sampling prior. It does not establish residence, qualifications, or eligibility. Preferences influence the soft objective and do not remove pairs from `A`.

Availability and preference generation use separate RNG objects initialized with the seed. Changing `flip_rate` (see [2.1](2.1.md)) therefore does not change preference labels. Sampling in sorted staff-ID order keeps each person's result stable when input indices are reordered.

The preference of person `i` is stored as `preferences[i]` in the `Instance`, the parameter `pref_i` in the notation of [2.1](2.1.md).

## 5. Weight mapping

The code calls `tools.make_seed.soft_weights(TEAM_ID)` instead of hard-coding numeric weights. `_team_seed` checks that the seed belongs to the same team ID.

| Weight | Current value | V1 mapping       |
| ------ | ------------- | ---------------- |
| `w1`   | 0.84          | Location penalty |
| `w2`   | 1.90          | Fatigue penalty  |
| `w3`   | 1.97          | Travel penalty   |

The `Instance` stores the weights as `soft_weights` in the official generator's order, and the `soft_weight_map` property names them `location`, `fatigue`, and `travel`.

All three weights must be used in the downstream objective/penalties. Returning or printing them alone does not complete the requirement. The objective and soft-constraint owners define and apply the penalty expressions.

## 6. CSV export

`write_preferences(inst)` exports the labels already stored in the instance to a CSV with columns `staff_id, preference, seed, source`. Every row has `source=simulated`. The function does not sample again. This file records input parameters, not optimized assignments.

## 7. Explanation of each function

### `simulate_preferences(data, seed)`

Count baseline campus frequencies and sample one label per person using a separate seeded RNG. Return labels in `staff_ids` index order, although draws occur in sorted staff-ID order.

### `write_preferences(inst, path=...)`

Export the already generated preferences, seed, and `simulated` source marker to the selected CSV path. Do not resample or write a schedule.

### `_team_seed(seed=None)`

Read `data/seed.txt` when no seed is supplied. Validate that the seed is an integer and equals the official value for `TEAM_ID`. Rejecting another seed prevents mixing one team's simulated inputs with another team's weights.

### `build_instance(...)` — preference and weight part

`build_instance` calls the M1 loader unless prepared scenario data is supplied, then calls `simulate_preferences` and `soft_weights(TEAM_ID)` and stores both in the returned `Instance`. It does not export the CSV; call `write_preferences(inst)` explicitly. The rest of its behavior is described in [2.1](2.1.md).

`small_slice` and the other helpers in [2.1](2.1.md) copy existing preferences and weights without resampling.

## 8. Running the export

From the repository root, with the pinned requirements installed:

```powershell
python -m m2_ilp.instance
```

This reads `data/seed.txt`, prints the preference counts and weight mapping, and writes `data/simulated_preferences.csv`. It does not write the optimized schedule or final metrics.

Do not change the seed or simulation rule after viewing solver results merely to select a better-looking outcome.
