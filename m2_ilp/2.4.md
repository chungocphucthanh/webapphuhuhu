# 2.4 Hard constraints and the independent validator

> Owner: TV2 Chu Ngọc Phúc Thành. Code: [hard.py](hard.py), [validate.py](validate.py).
> Tests: [test_hard.py](test_hard.py), [test_validate.py](test_validate.py).

Every schedule must satisfy the three hard rules H1–H3 taken over from Module 1. A schedule
that breaks any one of them is infeasible, whatever its fairness or penalties.

## 1. The three hard constraints

### H1 – Availability

A person cannot work a session they are not available for:

$$x_{ij} = 0 \qquad \forall (i, j) \notin A.$$

**Implementation.** [2.2](2.2.md) creates $x_{ij}$ only for $(i, j) \in A$ (2,593 variables),
so a pair outside $A$ has no variable and is $0$ by construction. This saves the
$6{,}059 - 2{,}593 = 3{,}466$ rows $x_{ij} = 0$ a dense model would need. H1 therefore adds
no rows; `add_hard_constraints` only asserts that every variable it receives lies in $A$ and
raises `AssertionError` otherwise.

### H2 – No double-booking

A person cannot work two sessions whose times intersect. Sessions $j$ and $k$ overlap when
$start_j < end_k$ and $start_k < end_j$; sessions that only touch at an endpoint
($end_j = start_k$) do not overlap, as in M1 (forum d=33630). $O$ is the set of overlapping
pairs from M1.

M1 states H2 pairwise: $x_{ij} + x_{ik} \le 1$ for every $(j, k) \in O$. `hard.py` uses the
equivalent clique form instead. For every person $i$ and every maximal clique $g$ of the
overlap graph:

$$\sum_{j \in g,\ (i,j) \in A} x_{ij} \le 1,$$

added only when at least two sessions of $g$ are in $A_i$. `maximal_cliques` sweeps the session
start times: the sessions running at a start time pairwise overlap, and keeping the sets that
are not contained in another gives exactly the maximal cliques (intervals have the Helly
property). It then checks that the cliques cover exactly the pairs in $O$ and raises
`ValueError` if the intervals and M1's overlap list disagree.

- **Both forms accept the same integer schedules, but cliques need fewer rows and a smaller LP.**
  On the 4-session `clique_instance`, three of whose sessions overlap pairwise, the clique form
  needs 3 rows (one per person) instead of 7 pairwise rows, and the clique row is tighter for the LP:
  $x = \tfrac12$ on the three sessions satisfies every pairwise row ($\tfrac12 + \tfrac12 \le 1$)
  but not the clique row ($\tfrac32 > 1$).
- **On the real data both forms are the same.** $O$ has 18 pairs, and each is the two campuses
  of one shift code at identical times. All 18 maximal cliques are pairs, so the clique form and
  the pairwise form give the same **642 H2 rows** on the sparse $x$. A dense pairwise model
  over all $73 \times 18$ person–pair combinations would need 1,314.

### H3 – Exact capacity

Each session $j$ gets exactly its demand $r_j$:

$$\sum_{i:\,(i, j) \in A} x_{ij} = r_j \qquad \forall j \in J.$$

- One equality per session: **83 rows** (45 sessions at CS1, 38 at CS2).
- Total demand $\sum_j r_j = 769$. Following M1, every duty in the dataset (`CBCT`,
  `Thư ký`, `Trưởng HĐ`) counts towards the same $r_j$; there is no role or eligibility rule.
- Under the elastic diagnosis of [2.8](2.8.md) (`config.elastic`), the row becomes
  $\sum_i x_{ij} + u_j = r_j$ with $u_j \ge 0$. This is used only to explain infeasibility,
  never for the delivered schedule.

## 3. The independent validator: `validate.py`

`check_schedule(inst, assigned)` takes a set of `(i, j)` pairs and returns every violated hard
rule as a readable message; an empty list means the schedule is valid. It is plain Python on the
`Instance` data and never imports PuLP, `model` or `hard`, so a bug in the ILP cannot hide
itself (`test_validator_stays_independent_of_the_ilp` checks the imports).

It checks, in order:

1. **H1.** A pair whose indices are not integers inside the instance gives
   `H1: assignment (9, 0) is outside the instance`. A pair outside $A$ gives
   `H1: CB1 is not available for Morning (2026-05-18 07:00-09:00)`.
2. **H2.** For every person and every pair in `inst.overlaps`, the pairwise rule exactly as M1
   states it, not the cliques of `hard.py`:
   `H2: CB2 works S0 and S1, 08:00-10:00 and 09:00-11:00 on 2026-05-18`.
   When both sessions have the same times, the message says `both 13:00-15:30`.
3. **H3.** The number of people in each session against `inst.demand[j]`, for both too few and
   too many: `H3: Morning needs 2 staff, got 3`.

The validator checks a set of pairs, so it judges integer schedules only; it cannot see a
fractional LP value such as $x_{ij} = \tfrac13$ (see [2.10](2.10.md), counterexample (b)).

### Gatekeeper role

The week-03 meeting (2026-09-22, MEETINGS.md) decided that M2 writes its outputs only after
the validator reports no violation. `run_m2` ([2.7](2.7.md)) calls `check_schedule` on the solved
schedule; on any violation it raises `RuntimeError` with up to 20 messages and writes neither
`schedule.csv` nor `metrics.json`. On the team's instance the validator reports 0 violations, and
the historical baseline is also valid under both the `seeded` and `day` availability policies.

## 4. Consistency with Module 1

The hard rules are the rows of M1's logic-to-linear bridge (`m1_logic/linear_bridge.py`,
DECISIONS.md), with M1's $d_j$ written $r_j$ here:

| Rule | First-order formula (M1) | Clause / CNF (M1) | 0/1 linear form (M2) |
|---|---|---|---|
| H1 | $\forall i,j:\ Busy(i,j) \to \neg Assign(i,j)$ | $\neg Assign(i,j)$ | no variable outside $A$ (M1: $x_{ij} = 0$) |
| H2 | $\forall i,j,k:\ Overlap(j,k) \land Assign(i,j) \to \neg Assign(i,k)$ | $\neg Assign(i,j) \lor \neg Assign(i,k)$ | clique row; pairwise $x_{ij} + x_{ik} \le 1$ on the real data |
| H3 | $\forall j:$ exactly $r_j$ staff $i$ satisfy $Assign(i,j)$ | sequential counter (auxiliary variables) | $\sum_i x_{ij} = r_j$ |

`test_hard_py_m1_bridge_and_validator_accept_the_same_schedules` checks this exhaustively. On
`clique_instance` (3 staff × 4 sessions = 12 pairs) it enumerates all $2^{12}$ schedules. It
checks that the rows of `hard.py`, M1's `encode_invigilator_assignment_linear` and
`check_schedule` accept exactly the same set, which is neither empty nor everything.
