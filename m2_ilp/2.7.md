# M2 requirement 2.7: Model assembly, solver, and outputs

**Owner:** 2551896 Hung — TV3.  
**Scope:** requirement 2.7 — assemble the ILP, solve it with a MILP solver, validate the schedule, and write the graded outputs.  
**Related parts:** [2.2 Decision variables](2.2.md) · [2.3 Objective function](2.3.md) · [2.9 Performance](2.9.md)

Hung joins the four model builders into one PuLP problem, solves it in two stages with CBC, passes the schedule to the independent validator, and writes `schedule.csv` and `metrics.json` for the autograder. The same code drives the counterexample (2.10), the infeasibility diagnosis and sensitivity runs (2.8), and the performance measurements (2.9): each of them is the main model with one configuration flag changed.

```text
load_dataset() (M1) + seed -> Instance (2.1, 2.6)
  -> create_variables: x_ij, w_i                 (2.2)
  -> add_hard_constraints: H1, H2, H3            (2.4)
  -> add_soft_terms: LOC, FAT, TRV               (2.5; stage 2 with use_soft only)
  -> add_objective: stage 1 or stage 2           (2.3)

  -> check_schedule, independent of the model    (2.4)
  -> schedule.csv, metrics.json                  (2.7)
  -> counterexample.json (2.10), tuning.json (2.8), performance.json (2.9)
```

`model.py` imports `variables` (2.2), `hard` (2.4), `soft` (2.5) and `objective` (2.3). `run.py` also imports `validate` (2.4) and `counterexample` (2.10), `tuning` (2.8) and `performance` (2.9). Stage `m2` therefore runs only when all of these modules are present.

## 3. Shared configuration: `config.py`

`config.py` uses the standard library only, so every module can import it without import cycles.

| Constant | Value | Use |
| --- | --- | --- |

`ModelConfig` is a frozen dataclass. Every variant is derived with `dataclasses.replace(config, ...)`, so the main model, the wrong models, the diagnosis and the sensitivity runs share one code path and differ only in one field.

| Field | Default | Meaning | Main user |
| --- | --- | --- | --- |
| `stage` | `1` | 1: minimize $t$; 2: minimize L1 plus soft penalties under $t \le t_{cap}$ | `solve` |
| `t_cap` | `None` | Stage-1 optimum $t^*$; required in stage 2 | `solve` |
| `use_soft` | `True` | Add LOC, FAT and TRV in stage 2 | 2.5, 2.10 |
| `relax_integrality` | `False` | $x_{ij}$ continuous in $[0,1]$ | 2.9 LP bounds, 2.10 (b) |
| `drop_overlap` | `False` | Omit H2 | 2.10 (a) only |
| `elastic` | `False` | H3 becomes $\sum_i x_{ij} + u_j = r_j$ | 2.8 diagnosis only |
| `elastic_penalty` | `1000.0` | $M_{el}$, the penalty on $\sum_j u_j$ | 2.8 |
| `fatigue_k` | `3` | Fatigue threshold $K$, fitted in 2.5 | 2.5, 2.8 |
| `weight_scale` | `(1.0, 1.0, 1.0)` | Factor applied to each soft weight | 2.8 sensitivity |
| `l1_chord` | `True` | DEVC rows (see [2.3](2.3.md)); `False` only for the 2.9 ablation | 2.3, 2.9 |
| `time_limit` | `120` | Seconds per stage | `run_cbc` |

| `threads` | `1` | One CBC thread for reproducible runs | `run_cbc` |
| `msg` | `False` | Show CBC and builder output | Debugging |

`__post_init__` raises `ValueError` for a stage other than 1 or 2, a negative or Boolean `t_cap`, a flag that is not `True`/`False`, a `fatigue_k` that is not a non-negative integer, a `weight_scale` that is not three non-negative factors, or a non-positive penalty, time limit or thread count.

`lambdas(inst)` returns $(\lambda_{LOC}, \lambda_{FAT}, \lambda_{TRV})$: `inst.soft_weights` multiplied element-wise by `weight_scale`. For our team ID the weights are 0.84, 1.9 and 1.97; the code reads them from `tools.make_seed` and never copies them (see [2.6](2.6.md)).

## 4. Assembling the model: `model.py`

`build_model(inst, config)` returns `(prob, x, handles)` and always calls the builders in this order:

1. `create_variables` (2.2): $x_{ij}$ for $(i,j) \in A$ and the expression $w_i = \sum_j x_{ij}$.
2. `add_hard_constraints` (2.4): the H1 check, H2 and H3.
3. `add_soft_terms` (2.5): only when `stage == 2` and `use_soft`.
4. `add_objective` (2.3): the stage-1 or stage-2 objective and its rows, plus $M_{el}\sum_j u_j$ when elastic.

Stage 2 without `t_cap` raises `ValueError`. `create_variables` prints $|A|$ against $|I| \cdot |J|$ on every call; tuning builds dozens of models, so `build_model` captures that line and prints it only when `config.msg` is set, and `run.py` prints the count once per run.

### Naming convention

Every variable and row is named `<family>_<indices>` with integer indices. The family is the text before the first underscore (`model.family`). `build_model` counts `n_vars` and `n_rows` by family, ignoring PuLP's `__dummy` placeholder, and the 2.9 size tables use these counts directly. For cross-checking with M1, `x_{i}_{j}` corresponds to M1 variable ID $i \cdot M + j + 1$ (`LinearModel.var(i, j)` in `m1_logic/linear_bridge.py`).

### `ModelHandles`

| Field | Content |
| --- | --- |
| `w` | $i \mapsto w_i$, a sum expression |
| `t` | The max-load variable |
| `dev` | $i \mapsto \delta_i$; empty in stage 1 |
| `l1` | $\sum_i \delta_i$; `None` in stage 1 |
| `soft_terms` | Unweighted `location`, `fatigue` and `travel` expressions, or `None` |
| `soft` | Weighted soft sum, or `None` when soft terms are off |
| `slack` | $j \mapsto u_j$; empty unless elastic |
| `cliques` | Maximal cliques used by H2 |
| `n_vars`, `n_rows` | Counts by family |
| `h2_pairwise` | Rows that M1's pairwise no-overlap form would need on the same $x$ |

### The complete model

Stage 1:

$$\min\ t \quad \text{s.t. H2, H3, MAX}, \qquad x_{ij} \in \{0,1\} \ \text{for } (i,j) \in A.$$

Stage 2, with $t^*$ from stage 1:

$$\min\ \sum_{i \in I} \delta_i + \lambda_{LOC}\,LOC + \lambda_{FAT}\,FAT + \lambda_{TRV}\,TRV$$

subject to H2, H3, MAX, TCAP ($t \le t^*$), DEVP, DEVN, DEVC, FAT, TRVZ and TRV. The objective terms are explained in [2.3](2.3.md).

| Family | Kind | Definition | Requirement | Stage 1 | Stage 2 |
| --- | --- | --- | --- | ---: | ---: |
| `x` | Variable | Binary $x_{ij}$ for $(i,j) \in A$ | 2.2 | 2,593 | 2,593 |
| `t` | Variable | $t \ge 0$ | 2.3 | 1 | 1 |
| `dev` | Variable | $\delta_i \ge 0$ | 2.3 | 0 | 73 |
| `s` | Variable | $s_{id} \ge 0$, sessions of $i$ on day $d$ above $K$ | 2.5 | 0 | 207 |
| `z` | Variable | $z_{idc} \in [0,1]$, $i$ works campus $c$ on day $d$ | 2.5 | 0 | 1,002 |
| `v` | Variable | $v_{id} \ge 0$, $i$ works both campuses on day $d$ | 2.5 | 0 | 501 |
| `u` | Variable | $u_j \ge 0$, missing staff in session $j$ | 2.4, 2.8 | elastic only (83) | elastic only (83) |
| `H2` | Row | $\sum_{j \in g \cap A_i} x_{ij} \le 1$ for each person $i$ and maximal clique $g$ | 2.4 | 642 | 642 |
| `H3` | Row | $\sum_{i \in A_j} x_{ij} = r_j$ | 2.4 | 83 | 83 |
| `MAX` | Row | $w_i \le t$ | 2.3 | 73 | 73 |
| `TCAP` | Row | $t \le t^*$ | 2.3 | 0 | 1 |
| `DEVP`, `DEVN` | Rows | $\delta_i \ge w_i - \bar w$ and $\delta_i \ge \bar w - w_i$ | 2.3 | 0 | 73 + 73 |
| `DEVC` | Row | Chord of $f(w) = \lvert w - \bar w \rvert$ between $\lfloor \bar w \rfloor$ and $\lfloor \bar w \rfloor + 1$ | 2.3 | 0 | 73 |
| `FAT` | Row | $s_{id} \ge \sum_{j \in J(d) \cap A_i} x_{ij} - K$ | 2.5 | 0 | 207 |
| `TRVZ` | Row | $z_{i,d(j),c(j)} \ge x_{ij}$ | 2.5 | 0 | 1,646 |
| `TRV` | Row | $v_{id} \ge z_{id1} + z_{id2} - 1$ | 2.5 | 0 | 501 |
| **Total** | | Variables / rows, without elastic slack | | 2,594 / 798 | 4,377 / 3,372 |

H1 has no rows: variables exist only for $(i,j) \in A$, and `add_hard_constraints` raises `AssertionError` if any variable lies outside $A$. On the real data every maximal clique is a pair (18 cliques of size 2), so the clique form and M1's pairwise form both give 642 H2 rows on the same $x$; the dense M1 encoding over all $73 \times 18$ person–overlap pairs would need 1,314.

## 5. Solver choice: PuLP + CBC

- **Why:** CBC is free and ships with PuLP, so nothing else has to be installed. The PuLP model reads like the mathematics, so every member can review it. CBC is a complete branch-and-cut MILP solver.
- **Settings:** `PULP_CBC_CMD(msg=False, timeLimit=120, gapRel=0, threads=1, logPath=...)`. With one thread, CBC follows the same search path on every run; with `gapRel=0`, "optimal" means proven optimal.
- **When to switch to OR-Tools CP-SAT:** only if CBC cannot prove optimality within the time limit on the full data, or when M3 needs automaton constraints (`AddAutomaton`). Neither applies today: both stages are proven optimal in under 0.3 s.

## 6. Two-stage solve: `solve.py`

`run_cbc(prob, config)` solves one problem and returns a `StageResult`:

| Field | Content |
| --- | --- |
| `status` | From `prob.sol_status`: 1 `optimal`, 2 `feasible`, −1 `infeasible`, anything else `not_solved` |
| `objective` | Objective value, or `None` without a solution |
| `runtime` | Wall-clock seconds |
| `gap` | Parsed from the CBC log line `Gap:`; 0.0 for an optimal run without that line; `None` when unknown |
| `nodes` | Parsed from `Enumerated nodes:`; 0 means solved at the root |

`solve(inst, config)` ignores `config.stage` and `config.t_cap`, and raises `ValueError` when `relax_integrality` is set (LP bounds use `build_model` and `run_cbc` directly). The lexicographic order itself is justified in [2.3](2.3.md).

1. Build and solve stage 1. If it is `infeasible` or `not_solved`, report it, call `tuning.diagnose` (elastic H3, requirement 2.8), print the sessions that are short of staff, and return a `Solution` with an empty schedule and the diagnosis.
2. Set $t^* = \operatorname{round}(t)$. A fractional $t$ raises `RuntimeError`; it cannot occur, because $t$ is minimized against integer loads.
3. Build stage 2 with `t_cap = t*` and solve it.
4. If stage 2 is `optimal`, or `feasible` after hitting the time limit, keep its schedule and record the gap. Otherwise fall back to the stage-1 schedule with status `feasible` and say so.

The returned `Solution` holds `status`, `assigned` (the frozenset of pairs with $x_{ij} > 0.5$), `t_star`, `objective` (`max_load`, `l1`, `location`, `fatigue`, `travel`, `total`), `stages` (`{1: StageResult, 2: StageResult}`) and `diagnosis` (`None` unless stage 1 failed).

## 7. Results on the full dataset

Seed `1358677812`, seeded availability with `flip_rate=0.30`, $K = 3$, Python 3.9.6, PuLP 2.8.0. Runtimes depend on the machine; the other values do not.

| Stage | Variables | Rows | Status | Objective | Time |
| --- | ---: | ---: | --- | --- | ---: |
| 1: minimize $t$ | 2,594 | 798 | optimal | $t^* = 11$ | 0.07 s |
| 2: minimize L1 + penalties | 4,377 | 3,372 | optimal, gap 0 | 59.849 | 0.17 s |

Because loads are integers and total load equals total demand, $t^* \ge \lceil 769/73 \rceil = \lceil 10.534 \rceil = 11$. The solver reaches this bound, so a maximum load of 11 is globally optimal; every load is 10 or 11.

The baseline and M2 schedules are compared on the same instance, $K$ and weights:

| Metric | Baseline | M2 |
| --- | ---: | ---: |
| `max_load` | 19 | **11** |
| `min_load` | 3 | 10 |
| `spread` | 16 | 1 |
| L1 | 115.397 | 36.329 |
| LOC | 162 | 28 |
| FAT | 7 | 0 |
| TRV | 0 | 0 |
| Weighted objective | 264.777 | 59.849 |

`beats_baseline` is `true` because $11 < 19$.

**Effect of DEVC.** With the chord rows, stage 2 is solved at the root node and its LP bound equals the integer optimum, 59.849. Without them, the LP bound drops to 23.52 and CBC stops at a 30-second limit after about 2,900 nodes with a 13% gap. The schedule then depends on the time limit and is no longer reproducible, which is why DEVC is on by default.

## 8. Outputs and reproducibility: `run.py`

`run_m2(seed, out_dir=None, extras=True)` returns the metrics dictionary:

1. Build the instance with `build_instance(seed, "seeded")`. With `out_dir=None`, it writes to `m2_ilp/` and regenerates `data/simulated_preferences.csv`, which comes out byte-identical.
2. Fit $K$ with `fit_fatigue_k(inst)` (it gives 3) and call `solve`.
3. If there is no schedule, raise `RuntimeError` with the diagnosis; nothing is written.
4. Run `check_schedule` (2.4), a pure-Python validator that never imports PuLP or the model. On any violation, raise `RuntimeError` with up to 20 messages; nothing is written.
5. Write `schedule.csv` and `metrics.json`, then print the instance size, the result against the baseline, and the validator result.
6. With `extras`, regenerate `counterexample.json` (2.10), `tuning.json` (2.8) and `performance.json` (2.9).

**`schedule.csv`:** header `invigilator_id,session_id,assigned`; one row for every pair in $I \times J$ ($73 \times 83 = 6{,}059$ rows), ordered by $i$ then $j$; `session_id` is the session name, such as `20260518_5_CS1`; `assigned` is `0` or `1`. UTF-8 without BOM, `\n` line endings.

**`metrics.json`:** `compute_metrics` of the M2 schedule (see [2.9](2.9.md)) plus `baseline_max_load`, `beats_baseline` (`max_load < baseline_max_load`), `t_star`, `availability_mode`, `flip_rate`, `fatigue_k`, `seed` and `status`. `flip_rate` and `fatigue_k` are stored so that the instance can be rebuilt from the file. Keys are sorted, floats are rounded to 6 decimals, `indent=2`, with a trailing newline. Current values: `max_load` 11, `baseline_max_load` 19, `beats_baseline` true, `l1` 36.328767, `location` 28, `fatigue` 0, `travel` 0, `status` optimal.

Neither file contains a runtime, gap or timestamp, so two runs give the same SHA-256. `tuning.json` and `performance.json` contain runtimes, so only their runtime columns change between runs.

`python -m m2_ilp.run` runs the same stage on its own; `--seed` defaults to `data/seed.txt`, and `--no-extras` writes only `schedule.csv` and `metrics.json`.
